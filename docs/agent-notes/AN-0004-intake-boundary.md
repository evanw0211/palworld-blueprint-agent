# 入库边界：合并范围、归档收录、忽略清单

- **状态：** accepted
- **日期：** 2026-10-19
- **取代：** None
- **被取代：** None

原工作区里只有一小部分该进本仓库：可复现的工具链、版本锁定的数据、不可再生的记录。其余（另一条链路的资料、备份、暂存、历史产物）留在原地。这条边界决定了别人克隆后看到什么，也决定了历史记录会不会被死代码淹没。

## 背景

- 原工作区总量约 650 MB：`refs\` 约 318 MB（paldex、存档工具）、`staging\` 约 89 MB、`backups\` 约 77 MB、`tools\` 约 61 MB（多数是 `bin/obj` 构建产物）、`blueprints\` 约 53 MB、`viewer\` 约 48 MB（存档→据点三维重建，另一条链路）、`out\`（配种与据点自动化研究文档）。
- 若把 `blueprints\`、`viewer\`、`refs\` 整目录搬入，会带入被取代的探索脚本、重复网格与无关链路，读者无法判断哪些还能跑。

## 决策

1. **合并只收**：数据刷新工具源码与 `tooling/mappings/Palworld.usmap`、社区参考样例、冻结历史记录、渲染对照图。
2. **`archive/` 只收三类不可再生信息**：决策证据、事故记录、唯一且只读的验证手段；被取代的**可运行代码不进仓库**（原稿留在原工作区）。
3. **git 入库范围**：数据快照、`meshes/`、图标与拼图、工具源码与映射进库；`out/` 产物、`__pycache__`、.NET `bin/`/`obj/` 忽略（见 [.gitignore](../../.gitignore)）。
4. **大二进制直接入库**，不用 Git LFS 或 submodule：单机本地仓库，恢复成本优先；单文件上限约 10 MB，超限先评估能否重新生成。

## 被否方案

| 方案 | 否掉原因 |
|---|---|
| 整目录搬 `blueprints\` | 含被取代的探索脚本、重复网格与旧文档，会让读者以为还能执行 |
| 把 `viewer\`（约 48 MB）一起搬 | 存档解析→据点重建是另一条链路，与本仓库「数据、校验、导出」无关 |
| Git LFS 或 submodule 管大资源 | 单机使用，LFS 需要额外服务端与指针恢复流程，收益不抵成本 |
| 把探索脚本收进 `archive/` 当参考 | 不能执行的死代码只会误导；其结论已由研究记录保留 |

## 后果

### 正面

- 仓库约 100 MB（不含 `.git`），克隆即用；每条历史只有一份 owner。
- 归档层里没有可执行死代码，读者不会误跑。

### 负面

- 原工作区仍是部分资料的唯一持有者，取回需要人工操作。
- 单文件上限意味着未来导出超大网格时要先评估。

### 后续

- 新增内容按同一标准评估：先进 owner 目录，再决定是否值得进 `archive/`。

## 合规

不变量：`archive/` 不得出现可运行但已废弃的代码；不得入库来源不明、或超过单文件上限且无法再生的大二进制。执行者：合并与评审时的人工红线。
